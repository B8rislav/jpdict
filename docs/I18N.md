# I18N

Locales: `ru` (source of truth, default) and `en`. Both dictionaries are at full parity.

`uiLocale` (interface language, ru/en) is independent of `selectedLanguage` (study
language, jp/cn).

## Module layout

| File | Role |
|------|------|
| `src/shared/i18n/locale.ts` | `Locale` type, `LOCALES`, `DEFAULT_LOCALE`, `isLocale`, `detectLocale` — no dictionary imports, so server code can depend on it cheaply |
| `src/shared/i18n/dictionaries.ts` | `translate(locale, category, key)` and `createTranslate(locale)` — pure lookup |
| `src/shared/i18n/context.tsx` | `LocaleProvider`, `useT()`, `useLocale()` |
| `src/shared/i18n/server.ts` | `tServer` (an alias of `translate`) for `generateMetadata` and other code outside the React tree |
| `src/shared/i18n/{ru,en}.json` | The dictionaries |

## API

### In components — `useT()`

```tsx
import { useT } from '@/shared/i18n';

const MyView = () => {
  const t = useT();
  return <span>{t('ui', 'nav_login')}</span>; // "Войти" / "Log in"
};
```

`useLocale()` returns the active locale, for `Intl` formatting and API `def_lang` params.

### In pure functions — take `t` as a parameter

Helpers that format strings receive a bound translator rather than reaching for a global:

```ts
export function formatInterval(seconds: number, t: Translate): string { … }
```

This keeps them pure and lets their tests pick a language by passing one
(`createTranslate('en')`) instead of mutating shared state.

### In server code — `tServer(locale, category, key)`

```ts
const { uiLocale } = await readProfile();
const title = tServer(uiLocale, 'ui', 'meta_site_title');
```

### In effects / API clients — read the store

Effects aren't components, so they read `$userProfile.getState().uiLocale` and pass it
down as an argument (`fetchWords(value, language, defLang)`).

## Why context, not a module global

The locale used to live in a module-level `let currentLocale`, set via `setLocale()` from
a `$userProfile` watcher. Two problems, both removed:

1. **Cross-request leakage.** A module-level variable in a Node server process is shared
   by every concurrent SSR render. Two overlapping requests — one RU, one EN — could hand
   each other the wrong language, intermittently and unreproducibly.
2. **No reactivity.** `t()` read the variable at render time, so switching locale
   re-rendered nothing on its own. It worked only because `page.tsx` happened to
   subscribe to `$userProfile` and re-render the whole tree.

Context is per-render-tree, so SSR can't cross-contaminate, and only components that
actually translate re-render on a locale change. `setLocale` / `getLocale` no longer exist.

## Locale resolution

```
DB profile (authenticated)  →  `profile` cookie  →  Accept-Language  →  'ru'
      authoritative              fast, SSR-readable   first visit only    fallback
```

`detectLocale` parses `Accept-Language` **with q-values**. The previous implementation
tested `/\ben[-_]/` against the whole header, so it returned English whenever English
appeared anywhere in the list — `ru-RU,ru;q=0.9,en-US;q=0.8` (stock Chrome on a Russian
system) served Russian users an English UI. Covered by `src/shared/i18n/locale.test.ts`.

A stored preference always wins over the browser's languages: a Russian speaker running
an English OS must not be forced into an English UI.

## `<html lang>` and `data-lang`

Both are set **server-side** in `src/app/layout.tsx` from the resolved profile:

```tsx
<html lang={profile.uiLocale} data-lang={profile.selectedLanguage ?? undefined}>
```

`data-lang` drives the CJK font swap (see [STYLING.md](STYLING.md)); `lang` is the
accessibility/SEO attribute. These were previously applied by a client component
(`HtmlLangSync`) in an effect after hydration, so the first paint always claimed the
wrong language. That component is gone.

## Storybook

`.storybook/preview.tsx` wraps every story in `LocaleProvider` + `ProfileProvider`, and
exposes both languages in the toolbar — so any view can be checked in either locale
without editing a story.

## Adding new strings

1. Add the key to `src/shared/i18n/ru.json` (Russian is the source of truth).
2. Add the matching key to `src/shared/i18n/en.json`.
3. Call `t('category', 'key')` in the component via `useT()`.

An ESLint rule (`no-restricted-syntax`) blocks Cyrillic string literals in `.tsx` files —
that error means "move it into the dictionaries". Note it does **not** cover `.ts` files,
so constants modules can still hide hardcoded copy.
